# `web/` — место под сайт

Сайт Koritsu — **React SPA на Vite, без своего сервера** (решение владельца §11).
Серверный рендер не нужен: сервис за логином, поисковикам там делать нечего.
Живёт сайт в этом же репозитории и выкатывается вместе с API; отдельного
контейнера у него нет — собранную статику отдаёт Caddy.

делался, делалось только место под него в `docker-compose.yml`.

## Что должно лежать в `web/dist`

Результат `npm run build` — то, что Vite кладёт в `dist/`:

    web/dist/index.html
    web/dist/assets/…            js и css с хешем в имени

`docker-compose.yml` монтирует этот каталог в контейнер Caddy как `/srv/web`
(только на чтение), а `Caddyfile` отдаёт его с `try_files {path} /index.html` —
адрес вроде `/projects/<uuid>` файлом на диске не является, и без этой строки
перезагрузка страницы давала бы 404.

Каталога может ещё не быть: тогда Caddy отвечает 404 на всё, кроме `/api/`, и
служба при этом работает — сайт и API поднимаются независимо.

## Как сайт разговаривает с API

Тот же домен, тот же origin (§3), поэтому CORS не нужен вовсе:

* `/api/…` — cookie-сессия плюс заголовок `X-CSRF-Token` на изменяющих
  запросах (§11);
* `/api/v1/…` — не для сайта: это внешний вход с Bearer-ключом;
* клиент TypeScript генерируется из OpenAPI (`/openapi.json`), а не пишется
  руками, — ради этого у службы и есть правило про `operation_id` и английские
  описания.

## Разработка

Vite поднимает свой сервер и ходит в API по открытому порту dev-окружения
(`docker-compose.dev.yml` публикует `127.0.0.1:8000`). Проксировать `/api` на
него — задача `vite.config.ts`, когда он появится.
