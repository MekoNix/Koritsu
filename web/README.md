# `web/` — сайт Koritsu

React SPA на Vite, **без своего сервера**. Серверный рендер не нужен: сервис за
логином, поисковикам там делать нечего. Живёт сайт в этом же репозитории и
выкатывается вместе с API; отдельного контейнера у него нет — собранную статику
отдаёт Caddy.

## Быстрый старт

Node 22 (nvm), pnpm 9.

    pnpm install
    API_PORT=8000 pnpm dev          # http://127.0.0.1:5173

Служба поднимается отдельно и по-настоящему:

    export PYTHONPATH=<корень>/packages
    export KORITSU_DATA_DIR=<временный каталог>
    export KORITSU_SECRET=<строка ≥ 32 байт>
    python -m api migrate
    python -m api serve --host 127.0.0.1 --port 8000
    python -m api worker            # отдельным процессом

`vite.config.ts` проксирует `/api`, `/openapi.json`, `/docs` и `/health` на
`http://127.0.0.1:${API_PORT:-8000}`. Прокси нужен не для удобства: cookie
сессии работает только на том же origin, и без него не было бы ни входа, ни
CSRF.

Проще всего поднять службу стендом — он же делает базу, воркер и подделку
модели одной строкой (подробности — `e2e/README.md`):

    bash e2e/stack.sh start /tmp/koritsu          # API 8006, подделка 8016
    API_PORT=8006 pnpm dev                        # сайт на 5173
    bash e2e/stack.sh stop /tmp/koritsu

Модель на стенде поддельная. Чтобы говорить с настоящей, не задавайте
`KORITSU_LLM_BASE_URL_DEEPSEEK` (подмена адреса — это она) и положите свой ключ:
общим — `KORITSU_PROVIDER_KEY_DEEPSEEK=<ключ>` в окружении службы и воркера, или
своим — в настройках сайта, «Ключи моделей».

## Команды

| Команда                             | Что делает                                             |
| ----------------------------------- | ------------------------------------------------------ |
| `pnpm dev`                          | Дев-сервер (порт `WEB_PORT`, по умолчанию 5173).       |
| `pnpm build`                        | Типы + сборка в `web/dist`.                            |
| `pnpm typecheck`                    | `tsc --noEmit` (вместе с `e2e/`).                      |
| `pnpm lint`                         | ESLint, предупреждения тоже считаются ошибкой.         |
| `pnpm format:check` / `pnpm format` | Prettier.                                              |
| `pnpm test`                         | Vitest — модульные проверки рядом с кодом.             |
| `pnpm e2e`                          | Playwright: браузер против настоящей службы на стенде. |
| `pnpm e2e:dist`                     | То же, но по собранному `dist` (нужен `pnpm build`).   |
| `pnpm preview`                      | Показать собранный `dist` (порт `PREVIEW_PORT`, 4173). |
| `pnpm gen:api`                      | `openapi.json` со службы → `src/api/schema.d.ts`.      |

`pnpm gen:api` не требует поднятой службы: `scripts/openapi-dump.py` собирает
приложение сам, на временном томе. Питон берётся из `KORITSU_PYTHON`
(по умолчанию `python3`) — в этом репозитории это `.venv/bin/python`.

`pnpm e2e` тоже ничего не требует поднимать руками: стенд и дев-сервер
поднимаются и гасятся сами (`playwright.config.ts`, `e2e/README.md`).

`pnpm e2e:dist` — та же связка, но браузер ходит по **собранному** сайту, а не
по дев-серверу: только там есть деление на куски, ленивые `import()`,
обфускация и префикс пути. Собрать надо заранее (`pnpm build`), дальше
`pnpm e2e:dist` поднимет стенд и показ статики сам — см. `e2e/README.md`.

## Как это устроено

    web/
      index.html          разметка страницы и скрипт темы до первого рендера
      src/
        main.tsx          точка входа
        api/              клиент службы: cookie, CSRF, ошибки, SSE, хуки → api/README.md
        app/              роутер, охрана маршрутов, оболочка (сайдбар, шапка, крошки)
        features/         области, у каждой свой routes.tsx:
                            auth        вход, регистрация, подтверждение, сброс
                            dashboard   лента виджетов, `/`
                            projects    работы и материалы, `/projects`
                            reports     отчёты работ, `/reports`
                            diagrams    блок-схемы и UML, `/flowcharts`, `/uml`
                            settings    профиль, оформление, ключи, `/settings/*`
                            admin       люди, очередь, события, `/admin/*`
        i18n/             ru/*.json, склеиваются в один словарь автоматически
        theme/            тема, светлый/тёмный, шрифт, плотность
        ui/               общие компоненты на Radix + Tailwind → ui/README.md
        styles/           переменные тем и базовые правила
        lib/              мелочи без предметки (`cn`, `maskEmail`)
        test/             настройка Vitest
      e2e/                стенд и сквозные проверки браузером → e2e/README.md
      scripts/            `openapi-dump.py` для `pnpm gen:api`

Маршрут заводится в `features/<область>/routes.tsx`; `app/routes.tsx`
подключает список одной строкой на область. Перевод — своим файлом
`i18n/ru/<область>.json`, ключ = имя файла плюс путь внутри него. Голых
русских строк в JSX нет.

Пункты сайдбара строятся из `GET /api/modules` через таблицу
`app/shell/moduleLinks.ts`: модуль, которого служба не отдала или которому на
сайте ещё нет страницы, в меню не показывается вовсе. Ссылки на `/admin` нет ни
в меню, ни на дашборде — туда попадают прямым адресом и только с `is_admin`.
Агента в меню тоже нет: он не страница, а панель поверх текущего экрана.

Первый экран собирается **одним** запросом к службе (`GET /api/bootstrap`):
профиль, модули, расход, пространства и колокольчик приезжают вместе и
раскладываются по ключам кэша — подробности в `src/api/README.md`.

Тема — это только значения CSS-переменных (`styles/themes.css`), выставленные
на `<html>` атрибутами `data-theme` × `data-mode`. Tailwind настроен на эти же
переменные, поэтому ни один компонент не знает, какая тема включена. Тема,
режим, шрифт и плотность применяются до первого рендера — встроенным скриптом
в `index.html`, иначе страница мигает чужими цветами.

## Что сайт ждёт от службы

Тот же домен, тот же origin, поэтому CORS не нужен вовсе:

- `/api/…` — cookie-сессия плюс заголовок `X-CSRF-Token` на изменяющих
  запросах; и то и другое клиент делает сам;
- `/api/v1/…` — не для сайта: это внешний вход с Bearer-ключом;
- ошибки — `{"error": {code, message, where}}`, `message` по-английски; русский
  текст берётся по `code` из `src/i18n/ru/errors.json`;
- клиент TypeScript генерируется из OpenAPI, а не пишется руками, — ради этого
  у службы и есть правило про `operation_id` и английские описания.

## Проверки

Три уровня, и каждый ловит своё:

- `pnpm test` — Vitest рядом с кодом: разбор, форматирование, отдельные экраны
  с подменённой службой;
- `pnpm e2e` — Playwright: настоящий браузер против настоящей службы с очередью
  и воркером; подделан только поставщик модели. Ловит склейку областей и правила
  брифа (полоска у активного пункта, раскрытие меню, неготовые модули);
- `bash e2e/smoke.sh` — тот же путь curl'ом, без браузера: быстрая проверка, что
  жив сам стенд.

## Выкат

`pnpm build` кладёт результат в `web/dist`:

    web/dist/index.html
    web/dist/assets/…            js, css и шрифты с хешем в имени

### В бою: статика едет в образе

`web/Dockerfile` — многоступенчатая сборка, из которой в бой уезжают только
файлы:

| Ступень                   | Что делает                                                                                                          |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `node:22-alpine AS build` | pnpm через corepack (версия — из `packageManager` в `package.json`), `pnpm install --frozen-lockfile`, `pnpm build` |
| `caddy:2-alpine`          | `COPY --from=build /app/dist /srv/web` — и больше ничего                                                            |

В итоговом образе нет ни Node, ни pnpm, ни `node_modules`, ни исходников: одна
собранная статика поверх обычного Caddy. Этот же контейнер и есть прокси —
отдельного контейнера у сайта по-прежнему нет, а Caddy у нас всё равно стоит.
`scratch` с одними файлами пришлось бы возить в Caddy через том, а том кто-то
должен заполнять: третий контейнер-одноразка, порядок запуска и вопрос
«что делать со статикой прошлого выката, оставшейся в томе».

Контекст сборки — сам каталог `web/` (`docker-compose.yml`: `context: ./web`),
исключения — `web/.dockerignore`. Собирается всё вместе со службой:

    cp .env.example .env && $EDITOR .env       # один раз
    docker compose up -d --build

`Caddyfile` в образ не попадает: он монтируется файлом с хоста, поэтому смена
домена или белого списка адресов не требует пересборки сайта.

### Админка — на своём домене

Админка живёт на домене третьего уровня (`KORITSU_ADMIN_DOMAIN`), а не по
`/admin` того же сайта. Даёт это три вещи: белый список адресов накрывает
**всё** на этом имени (закрывать новый админский адрес отдельно не надо),
origin у админки свой — то есть своя cookie сессии, и вошедший на сайт не
оказывается вошедшим в админку заодно; и само имя не выводится из основного
перебором путей.

Знают об этом трое, и все трое берут строку из одной переменной:

| Кто    | Что делает                                                                     |
| ------ | ------------------------------------------------------------------------------ |
| Caddy  | свой блок на этом имени; на основном `/admin*` и `/api/admin/*` — 404          |
| Служба | на чужом `Host` маршруты `/api/admin/*` отвечают 404 (`Settings.admin_domain`) |
| Сайт   | `/admin*` открывается только с этого имени, иначе «страница не найдена»        |

Имя сайт получает от службы — полем `admin_domain` в `GET /api/bootstrap` (оно
же в `GET /api/auth/me`), а не из сборки: строка живёт в `.env` на машине, и
вписывать её в статику значило бы пересобирать сайт ради настройки. Ссылка в
меню пользователя ведёт на это имя обычным переходом браузера — между
origin'ами роутер не ходит.

За прокси служба берёт имя из `X-Forwarded-Host`, и **только** при
`KORITSU_TRUST_PROXY=yes`: заголовок пишет кто угодно, и на открытом порту
поверить ему значило бы отдать админку одной строкой в curl.

Строки нет — домена у админки нет: снаружи она закрыта совсем (Caddy отвечает
404 и на `/admin`, и на `/api/admin/*`), а служба и сайт ведут себя как раньше,
по флагу `is_admin`. Это рабочее состояние машины без домена: `docker compose
up` поднимается и без этой строки, потому что умолчание блока —
`admin.koritsu.example`, имя из зарезервированной зоны, которого нет в DNS.

### Адрес без домена: префикс пути

Домена у сайта пока нет, поэтому адрес — IP машины плюс случайная строка в
пути, чтобы сайт не нашли перебором:

    http://203.0.113.7/k7f3x9/

Ни IP, ни строка в репозиторий не попадают: обе живут в `.env` на машине, а в
`Caddyfile` и `docker-compose.yml` стоят подстановки (`KORITSU_DOMAIN`,
`KORITSU_BASE_PATH`). Тесты `tests/api/test_deploy.py` за этим следят прямо —
любой настоящий IP или чужое имя в файлах выката роняют прогон.

Под префиксом живёт **всё разом** — и страницы, и `/api`: cookie сессии одна на
двоих, и разъехавшиеся пути означали бы вход, который не работает. Складывается
это из трёх мест, и все три получают значение из одной строки `.env`:

| Где             | Что                                                                               |
| --------------- | --------------------------------------------------------------------------------- |
| Caddy           | `handle_path {$KORITSU_BASE_PATH}/*` снимает префикс один раз                     |
| Vite            | `base` из `VITE_BASE_PATH` — ссылки в `index.html` и на `assets/`                 |
| Роутер и клиент | `basename` и адрес службы — из `import.meta.env.BASE_URL` (`src/lib/basePath.ts`) |

Собрать сайт под префиксом руками:

    VITE_BASE_PATH=/k7f3x9 pnpm build

Через compose то же самое приезжает аргументом сборки (`build.args`), потому что
Vite вписывает префикс **на сборке**: у готового образа его не поменять, только
пересобрать. Всё, что собирает адрес службы мимо клиента API (потоки SSE,
ссылки на артефакты и материалы), обязано идти через `withBase` из
`src/lib/basePath.ts`.

Без переменной префикс пуст, и `pnpm dev`, `pnpm test`, `pnpm e2e` работают
ровно как раньше.

### Обфускация и карты исходников

`vite build` в режиме `production` пропускает готовые куски через
`rollup-plugin-obfuscator` — код режется на части и обфусцируется:
переименование имён и укрытие строк. `debugProtection` и `selfDefending`
намеренно выключены — они ломают отладчик и автоматический
браузер; `controlFlowFlattening` тоже, это кратный рост размера ради защиты,
которую всё равно снимают за вечер. Обфускация — задержка чужого чтения, а не
запрет: всё, что должно быть тайной, живёт в службе.

Отладить боевую сборку:

    KORITSU_OBFUSCATE=0 pnpm build

Карты исходников в `production` не собираются вовсе: карта рядом с
обфусцированным кодом снимала бы обфускацию одним кликом.

### Деление на куски

`src/app/areas.tsx` грузит область сайта своим `import()` по первому отрезку
адреса, поэтому вход тянет только оболочку, а CodeMirror приезжает лишь на
схемах и на правке нетекстовых тегов. Завели область с новым первым отрезком
адреса — допишите строку в `ЗАГРУЗЧИКИ` там же; забыли — сработает запасной
путь (грузятся все куски), то есть будет чуть медленнее, а не сломано.

### Что делает Caddy

Блоков сайта два: основное имя и имя админки.

На основном имени (`KORITSU_DOMAIN`):

    /robots.txt             «Disallow: /» — и он один живёт в корне
    {префикс}/…             всё остальное, ниже — уже без префикса
    /admin*, /api/admin/*   404 всегда: админка живёт на своём имени
    /api/v1/*               → api:8000, мимо Anubis (внешние ключи, не браузеры)
    /api/*, /health,        → api:8000
    /openapi.json, /docs
    всё остальное           → anubis:8923 → caddy:8080 → /srv/web
    корень мимо префикса    → 404 без подробностей

На имени админки (`KORITSU_ADMIN_DOMAIN`) — то же самое, но целиком под белым
списком адресов и без Anubis:

    адрес не в KORITSU_ADMIN_ALLOW  → 404 на весь блок, что бы ни спросили
    {префикс}/api/*                 → api:8000
    {префикс}/…                     → /srv/web (тот же собранный сайт)
    корень мимо префикса            → 404 без подробностей

Статика отдаётся с `try_files {path} /index.html`: адрес вроде
`/projects/<uuid>` файлом на диске не является, и без этой строки перезагрузка
страницы давала бы 404. Заголовки кэша — разные: `assets/*` носят хеш
содержимого и отдаются с `max-age=31536000, immutable`, всё остальное (то есть
`index.html`, он же любая страница) — с `no-cache`, иначе выката неделю никто
не увидит.

### Переменные

`KORITSU_ADMIN_ALLOW` — белый список адресов админки; путь у неё
`.env` → `docker-compose.yml` → `Caddyfile`, и служба её не читает вовсе.
Значение — CIDR **через пробел**:

    KORITSU_ADMIN_ALLOW=203.0.113.7/32 2001:db8::/64

Через запятую Caddy список не поймёт и не поднимется — это лучше, чем принять
строку и не пустить владельца в его же админку. Пусто или строки нет вовсе —
петля, то есть снаружи админка закрыта всем; **в бою строку надо заполнить
своим адресом**, иначе в неё не попасть и владельцу. Список закрывает весь блок
имени админки целиком — и страницы, и `/api`.

`KORITSU_ADMIN_DOMAIN` — имя домена админки (`admin.koritsu.example`). Читают
его двое: `docker-compose.yml` → `Caddyfile` (адрес блока) и сама служба (на
чужом `Host` — 404). Схему и порт писать не обязательно, служба их срезает.
Пусто — админка на своём домене не живёт (см. выше).

`KORITSU_DOMAIN` — адрес сайта целиком, вместе со схемой: `http://203.0.113.7`
на время теста (тогда TLS не выпускается вовсе) или `koritsu.example`, когда
появится домен. `KORITSU_BASE_PATH` — префикс пути (`/k7f3x9`, без косой на
конце; пусто — сайт в корне), `VITE_BASE_PATH` — он же для сборки, с косой на
конце. Две последние строки **обязаны сходиться**: разойдясь, они дадут
страницу, которая загрузится и не заработает.

`KORITSU_BASE_URL` — адрес в письмах, тот же и **вместе с префиксом**
(`http://203.0.113.7/k7f3x9`): служба его не складывает из кусков, а берёт как
есть.

`KORITSU_COOKIE_SECURE=no` — на время теста без домена. По HTTP браузер cookie
с флагом `Secure` не сохраняет, и человек входил бы в форму входа. Появится
HTTPS — строку стереть.

Белый список — второй замок, а не замена первому: флаг `is_admin` в службе
остаётся, `/api/admin/*` без него не работает и с разрешённого адреса.

### На dev

`docker-compose.dev.yml` образ сайта не собирает (`build: !reset null`,
обычный `caddy:2-alpine`) и монтирует `web/dist` с диска: `pnpm build` — и
обновление видно перезагрузкой страницы, а не пересборкой образа.

    docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d
    # сайт и служба одним origin: http://127.0.0.1:8080

Порт 8080 попадает во внутренний блок `Caddyfile` (`:8080`), который отвечает
на любое имя и отдаёт и статику, и `/api` — cookie сессии живёт только на своём
origin. Каталога `web/dist` может ещё не быть: тогда Caddy отвечает 404 на всё,
кроме `/api/`, и служба при этом работает — сайт и API поднимаются независимо.
Админка на dev открыта всем адресам (порт и так поднят только на петлю хоста).

При разработке всё это не нужно: `pnpm dev` поднимает Vite со своим прокси на
`/api` (см. «Быстрый старт»).
