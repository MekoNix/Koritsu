# Стенд сквозных проверок: настоящая служба, поддельная модель

Здесь лежит то, на чём гоняются сквозные проверки сайта — свои (`smoke.sh`,
curl'ом) и Playwright'ом. Настоящее в нём всё, кроме поставщика модели:
служба (`api serve`), очередь с воркером (`api worker`), база на временном томе,
HTTP через сокет, cookie сессии, заслон CSRF, поток SSE. Подделан только тот, к
кому уезжает ключ, — и подделан по адресу, а не подменой кода.

    web/e2e/
      stack.sh            поднять / остановить / дождаться стенд
      stack-fg.sh         то же, но на переднем плане — для Playwright
      smoke.sh            проверка пути человека curl'ом (13 шагов)
      fake-llm/server.py  поддельная модель протокола `openai`
      tests/              сквозные проверки браузером (Playwright)

## Быстро

    bash web/e2e/stack.sh start /tmp/стенд     # том — аргумент или mktemp -d
    bash web/e2e/smoke.sh /tmp/стенд           # проверка пути человека
    bash web/e2e/stack.sh status               # кто жив, где логи
    bash web/e2e/stack.sh stop                 # остановить всё

Каталог тома можно не повторять: `start` запоминает его в `/tmp/koritsu-e2e-last`,
и `stop`, `wait`, `status`, `smoke.sh` берут его оттуда. Том остаётся после
`stop` — в нём логи, база и файлы проектов; сносить его можно руками.

Что поднимается и куда пишет:

| процесс      | порт (умолч.)      | журнал               |
| ------------ | ------------------ | -------------------- |
| `fake-llm`   | 8016 (`FAKE_PORT`) | `<том>/fake-llm.log` |
| `api serve`  | 8006 (`API_PORT`)  | `<том>/serve.log`    |
| `api worker` | —                  | `<том>/worker.log`   |

Порты стенда — не умолчания службы (8000): 8006 и 8016 отданы этому стенду
отдельно, чтобы параллельные запуски не толкались.

## Переменные

Стенда (`stack.sh`):

| переменная                             | умолч.                 | зачем                                    |
| -------------------------------------- | ---------------------- | ---------------------------------------- |
| `API_PORT`                             | 8006                   | порт службы                              |
| `FAKE_PORT`                            | 8016                   | порт поддельной модели                   |
| `PYTHON`                               | общий venv репозитория | интерпретатор                            |
| `FAKE_DELAY_MS`                        | 30                     | задержка между кусками потока у подделки |
| `FAKE_CHUNK`                           | 48                     | знаков в куске потока                    |
| `KORITSU_E2E_DIR`                      | —                      | том, если не назван аргументом           |
| `KORITSU_REGISTRATIONS_PER_IP_PER_DAY` | 1000                   | боевое число — 5, на стенде мало         |
| `KORITSU_ADMIN_DOMAIN`                 | `127.0.0.1`            | имя, на котором живёт админка            |

Службы — их выставляет `stack.sh` сам, смотреть `web/e2e/stack.sh env`:

    KORITSU_DATA_DIR            временный том (НЕ /data)
    KORITSU_SECRET              случайный, хранится в <том>/secret
    KORITSU_ENV=dev             без этого подмена адреса модели не работает
    KORITSU_TRUST_PROXY=no      порт открыт напрямую, без Caddy
    KORITSU_BASE_URL            адрес службы: из него ссылка в письме
    KORITSU_PROVIDER_KEY_DEEPSEEK=fake-key    общий ключ поставщика
    KORITSU_LLM_BASE_URL_DEEPSEEK=http://127.0.0.1:8016
    KORITSU_ADMIN_DOMAIN=127.0.0.1          имя, на котором живёт админка

Последняя строка делает стенд похожим на бой: админка вынесена на своё имя, и
на всяком другом `/api/admin/*` отвечает 404. Стенд смотрят по `127.0.0.1`,
поэтому там она открыта как обычно; открыв тот же сайт как `localhost`,
получаешь ровно то, что получит чужой снаружи, — админки нет. Пустая строка
(`KORITSU_ADMIN_DOMAIN= web/e2e/stack.sh start`) разделение выключает.

## Как служба попадает на подделку

Настройка `KORITSU_LLM_BASE_URL_<ПРЕСЕТ>` (`api/settings.py`) — единственная
правка службы ради стенда, и она dev-only:

- читается всегда, применяется только при `KORITSU_ENV=dev`
  (`Settings.llm_base_url`) — в `prod` возвращается `None`, и пресет собирается
  ровно тот же, что всегда;
- применяется в одном месте — `api/runs/model.py`, где пресет собирается на
  время задания (`llm.presets.make(..., base_url=…)`);
- при старте службы и воркера пишет предупреждение в журнал (`api.error`) —
  и когда подмена действует, и когда её нашли в `prod` и не применили.

Проверено тестами `tests/api/test_llm_base_url.py` (оба случая, dev и prod).

Пути без правок службы не нашлось: адрес зашит в пресет (`llm/presets.py`),
подпроцесс задания живёт с вычищенным окружением (`api/jobs/child.py`), так что
ни подмена провода (как в `tests/api/b_fixtures.py`), ни `HTTPS_PROXY` туда не
доедут; пресет `claude_cli_proba` (протокол `cli`, где `base_url` — это команда)
служба не пропускает вовсе — прогон разрешён только пресетам, у которых бывает
ключ (`keys.providers()`).

## Что умеет поддельная модель

Говорит по протоколу `openai` (`POST /v1/chat/completions`, поток SSE, `usage`,
`GET /v1/models`, `GET /health`). Ключ принимает любой — на стенде это слово
`fake-key`.

**Форму ответа берёт из запроса, а не из знания про Koritsu.** По порядку:

1. `response_format.json_schema` — строит объект по схеме;
2. `tool_choice: {function: set_values}` — то же, но вызовом инструмента
   (куски аргументов, как у настоящего потока);
3. схемы в запросе нет, но слой пересказал её словами
   («Требуемая структура ответа: …», `llm.structured.schema_hint` — так работает
   пресет `deepseek`, у него объявлен `json_object`) — описание разбирается
   обратно в схему;
4. ничего из этого — ответ словами.

Поэтому одинаково отвечают `fill_tag`, `fill_report` (теги закрываются по
одному, поток идёт кусками), вопросы `kadai` и всё, что появится позже со своей
схемой. Имена тегов вычитываются из промпта — только затем, чтобы текст на
экране был про дело («раздел «цель» …»).

**Ошибки по требованию.** Маркер в любом месте запроса (задача агента, значение
соседнего тега, имя проекта — что угодно, что доедет до модели):

| маркер         | что делает                                                         |
| -------------- | ------------------------------------------------------------------ |
| `[[FAKE:429]]` | 429 с `Retry-After: 1` — слой повторит по своей политике и сдастся |
| `[[FAKE:500]]` | 500                                                                |
| `[[FAKE:ERR]]` | 200 и ошибка **полем внутри потока** — так делают шлюзы            |

В `smoke.sh` этим проверяется путь беды: маркер кладётся значением соседнего
тега, задание кончается `failed` с кодом `run_failed`.

**Ходы инструментами по требованию — `[[FAKE:TOOLS]]`.** Без принуждения
(`tool_choice`) подделка на объявленные инструменты отвечает словами, и прогон
уровня 3 проходит вхолостую: ни `tag_closed` в потоке, ни `result.filled`.
Маркер в задаче агента («что поменять» в окне Ctrl+J) просит её сделать то, что
делает модель, — и петля идёт ровно два хода:

1. вызовы объявленного инструмента (по одному на каждый тег из промпта, не
   больше двух) — служба ставит значения и шлёт `tag_closed`;
2. итог словами — им петля и заканчивается (`outcome: done`).

Вслепую подделка по-прежнему не зовёт. Инструмент выбирается тот, чьи
обязательные аргументы можно заполнить из самого запроса: без аргументов вызов
до петли не доезжает (`llm.loop` считает `{}` битым JSON), а идентификатор
материала или исходник программы взять неоткуда — остаётся тот, что просит
`key`, и ключи названы в промпте («Заполни теги: [цель], [выводы]»). Тип
значения — из описи тегов там же («`[цель] цель — markdown …`»): значение тега
объявлено помеченным объединением по всем типам сразу, и ветка наугад не прошла
бы валидатор службы. Второй ход отличается от первого не памятью, а запросом —
в нём уже есть ответы инструментов (`role: tool`).

    curl -sS http://127.0.0.1:8010/health          # подделка жива
    # проверка целиком — e2e/tests/agent.spec.ts

Чего подделка не делает:

- **не зовёт инструменты «за модель» сама.** Без маркера `[[FAKE:TOOLS]]`
  объявленные инструменты остаются неназванными: она отвечает словами и тем
  заканчивает петлю. Прогон агента проходит (`outcome: done`, один ход), но
  тегов не ставит;
- **не говорит протоколом `anthropic`.** Подменять можно пресеты протокола
  `openai` — `deepseek` (так и настроено) и `openrouter`
  (`KORITSU_LLM_BASE_URL_OPENROUTER=http://127.0.0.1:8016`; свои поля тела
  шлюза подделка просто не читает). Для `anthropic` понадобился бы второй
  протокол — не понадобилось;
- **не ходит по стадиям `kadai` за человека.** Сценарий отказывает раньше
  модели, если к проекту не приложено условие задачи, — это его правило, а не
  наше: `kadai_run` без условия падает `422 kadai_failed` («условие задачи не
  приложено»). Приложите материал условием — и стадии пойдут на подделке.

## Для Playwright

Руками поднимать ничего не надо: `pnpm e2e` (из `web/`) поднимает стенд и сайт
сам — это две записи `webServer` в `web/playwright.config.ts`. Первая зовёт
`e2e/stack-fg.sh` (тот же `stack.sh`, но на переднем плане, чтобы Playwright мог
его погасить), вторая — `pnpm dev`. По концу прогона гасятся обе.

    cd web
    KORITSU_E2E_DIR=/tmp/мой-стенд pnpm e2e          # всё сразу
    pnpm e2e flow.spec.ts                            # одна проверка
    pnpm exec playwright show-trace test-results/…/trace.zip

Что где лежит:

    web/playwright.config.ts       порты, окно 1440×900, webServer, трассы
    web/playwright.dist.config.ts  то же, но по собранному `dist` (`pnpm e2e:dist`)
    web/e2e/stack-fg.sh            стенд на переднем плане
    web/e2e/tests/stand.ts         порты и том — один файл на конфиг и проверки
    web/e2e/tests/helpers.ts       словарь, свой человек, шаблон DOCX
    web/e2e/tests/*.spec.ts        сами проверки

## Боевая сборка: `pnpm e2e:dist`

`pnpm e2e` ходит по дев-серверу, а в бою сайт другой: он поделён на куски,
области грузятся ленивым `import()`, код обфусцирован и лежит под префиксом
пути. Ломается это молча — браузер просит кусок не по тому адресу, получает
`index.html`, и область не открывается вовсе, при том что страница входа
работает. Поэтому есть отдельная проверка: `web/e2e/tests/dist.spec.ts`.

    cd web
    VITE_BASE_PATH=<префикс> pnpm build     # префикс можно и не задавать
    pnpm e2e:dist

Она проходит вход → дашборд → проект → отчёт → схему и требует, чтобы браузер
не пожаловался ни на один кусок. Сборку проверка не делает намеренно: префикс
задаётся на сборке, и пересобирать чужой `dist` под свои умолчания значило бы
проверять не то, что выкатывают. Префикс она вычитывает из самого `dist`
(`index.html`), поэтому задавать его второй раз не надо.

Статику отдаёт `vite preview` (`preview` в `web/vite.config.ts`): тот же
префикс, что у сборки, и `/<префикс>/api` проксируется на службу с тем же
снятием префикса, что делает `handle_path` в `Caddyfile`. Порт показа —
`PREVIEW_PORT`, умолчание 4173. Обычный `pnpm e2e` эту проверку не подбирает
(`testIgnore`), а её трассы лежат отдельно, в `test-results-dist/`.

Порты и том берутся из окружения (`API_PORT`, `FAKE_PORT`, `WEB_PORT`,
`KORITSU_E2E_DIR`); умолчания — 8000, 8010, 5170 и `/tmp/koritsu-web-e2e`.
`reuseExistingServer` включён: стенд, поднятый руками для разглядывания глазами,
повторно не поднимается и после прогона не гасится.

**Версия `@playwright/test` закреплена точно** (`1.61.1`, без «`^`») — под сборку
браузера, что лежит в `~/.cache/ms-playwright` (`chromium-1228`). Версия выше
потребует другой сборки и её загрузки; проверить соответствие —
`pnpm exec playwright install --dry-run chromium`.

Токен подтверждения почты в `dev` берётся из журнала службы — `<том>/serve.log`,
строка со ссылкой `…/confirm?token=…` (`smoke.sh`, шаг 3, и `helpers.ts`
показывают как). Отдельной «ручки для тестов» у службы нет и заводить её нельзя:
путь подтверждения обязан быть тем же, каким он будет у человека. Право
администратора выдаётся так же честно — строкой `UPDATE users SET is_admin=1` в
базе тома (`admin.spec.ts`).

Каждая проверка должна заводить своего человека (почта с отметкой времени): том
общий, а вошедший — состояние. Боевой лимит регистраций с одного адреса (5 в
сутки) на стенде поднят до 1000 — иначе очередной прогон проверок упирался бы в
`429 rate_limited`. Проверять сам лимит — с боевым числом:
`KORITSU_REGISTRATIONS_PER_IP_PER_DAY=5 web/e2e/stack.sh start`.
