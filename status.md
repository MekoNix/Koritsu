## Дальше: 2.0.0a3 — hokoku и LLM

Две половины одной версии: шов, через который значения тегов приходят снаружи, и модель,
которая эти значения производит. Сайт и HTTP-сервер по-прежнему не делаем — нужен только шов,
чтобы потом endpoint с параметрами или скрипт подключились, ничего не переписывая.
Подробно — `ref/koritsu-hokoku-llm-api-2026-08-28.md`.

Про LLM, коротко (детали и цифры — в той же записке): модель производит **значения**, а не
документ, и никогда не видит OOXML, путей на диске и подпроцессов. Три уровня в порядке
внедрения: один тег (`messages.parse` по схеме одного значения) → весь отчёт одним вызовом
(теги связаны, N независимых вызовов дадут рассогласованный текст; префикс с файлами проекта
и манифестом кэшируется) → агент с инструментами (`list_project_files`, `read_file`,
`make_flowchart`, `make_class_diagram`, `make_object_diagram`, `set_tag`, `preview`) на штатном
`tool_runner`. Параметры вызова: `claude-opus-5`, `thinking={"type": "adaptive"}` (`budget_tokens`
на этой модели отклоняется с 400), глубина через `output_config={"effort": …}`, стриминг там,
где ответ длинный, попадание в кэш проверять по `usage.cache_read_input_tokens`. Артефакты
адресуются идентификаторами, не путями. Всё, что вернула модель, проходит тот же валидатор,
что и запрос из интерфейса.

- [ ] `hokoku/wire.py` — JSON ↔ типизированные значения. Сейчас `json.dumps({"схема":
      Image("a.png")})` падает, то есть значение тега нельзя ни передать по HTTP, ни получить
      от модели. Это единственный настоящий блокер, на нём висит всё остальное.
- [ ] `build_report(job: dict) -> dict` — единственная точка входа: чистый JSON внутрь,
      чистый JSON наружу. Ни HTTP, ни хранилища внутри.
- [ ] `python -m hokoku.build job.json` — скрипт: `json.load` → `build_report` → `json.dump`.
- [ ] Манифест шаблона: тип и промпт на каждый тег. По умолчанию всё `markdown`, манифест
      объявляет только исключения (`image`, `diagram`, `code`, `formula`, таблица как данные).
      Он же — то, что отдаётся модели вместо DOCX.
- [ ] `fragmos.generate_xml(...) -> str` — сейчас пишет в фиксированный `/tmp/fragmos_out.xml`
      и отдаёт путь, два одновременных запроса затрут друг друга. `uml.build_xml` уже отдаёт
      строку — привести к одному контракту.
- [ ] `docx_to_pdf` в варианте bytes → bytes.

## Действующие решения

Собраны в одно место; версия рядом с решением — когда договорились.

**hokoku (2026-08-27).** Свой движок на python-docx, не docxtpl. Только движок: хранилище
отчётов и профилей — позже и отдельно. Имя пакета — `hokoku` (было `tekton`). Логика в тегах
(`|умолчание`, `#if`, `#each`) — не сейчас, парсер синтаксис резервирует. Сноски: теги в них
не ищем, блоки не поддерживаем — оставляем как есть.

**Тип тега — манифест при шаблоне, а не соглашение по имени (2026-08-28).** Имя-префикс
(`global_` и т.п., как предполагалось 2026-08-27) ломает `{ref:ключ}` и сохранённые значения
при смене типа, и промпт девать некуда. Решение 2026-08-27 про префиксы отменено.

**uml_generator (2026-08-27).** Пользовательский код не выполняется: динамические бэкенды
objektis (exec в subprocess, `dotnet run`) удалены по соображениям безопасности. Остались
статические — `py_static`, `cs_static` (`Main()`), `cpp_static` (`main()`).

**Агенты и API (2026-08-28).**

- LLM производит значения, а не документ. Артефакты адресуются идентификаторами, не путями.
- Агент код не сочиняет — код приходит от пользователя, агент заполняет теги.
- Версионируем значения тегов, а не документ: история версий отчёта тогда бесплатна.
- Хранилище — диск + SQLite. Postgres и S3 выигрывают только на нескольких машинах.
- Ключи — и серверный с лимитом, и свой из настроек; свой перекрывает.
- LibreOffice остаётся подпроцессом: демон снимает 1.7 с, но течёт и заклинивает на кривом
  документе, унося следующие конвертации.
- Всё через очередь, синхронного рендера наружу нет.

**Модели подключаемые, лимит в токенах (2026-08-29).** Модель не одна и не обязательно
Anthropic: в настройках будет список endpoint'ов, совместимых с OpenAI и Anthropic, куда
можно вписать любую. Отсюда два следствия. Первое: **лимит пользователя считаем в токенах
системы**, а не в деньгах — цена у каждого endpoint своя и меняется, токены же одинаковы.
Второе, важное для проекта LLM-части: **нельзя опираться на фирменные возможности одного
поставщика**. Кэширование префикса, `effort`, adaptive thinking, операторский канал
`role: system` и штатная петля инструментов есть у Anthropic и отсутствуют у
OpenAI-совместимого endpoint'а. Значит либо тонкий слой с проверкой возможностей и честной
деградацией (без кэша дороже, без операторского канала слабее защита от инъекции), либо
эти возможности объявляются необязательными. Цифры стоимости в
`ref/koritsu-hokoku-llm-design-2026-08-28.md` посчитаны для Anthropic и на другом
поставщике не действуют.

**Сроки хранения промптов и файлов — отложено (2026-08-29).** Вопрос настоящий (наблюдаемость
против приватности), но решать его на этапе API, когда появится хранилище. Сейчас не
проектируем.

**Тема схем — под тему пользователя (2026-08-29).** Схема в интерфейсе следует теме, которую
выбрал пользователь; решается на этапе сайта, вместе с самими темами. Отчёт при этом остаётся
светлым независимо от темы интерфейса — носитель белый лист. Как это делается технически
(роли цветов `var(--роль, светлый hex)`, одна схема на все темы) — в
`ref/koritsu-drawio-themes-2026-08-28.md`.
