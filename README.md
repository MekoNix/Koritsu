# Koritsu 2.0 (beta)

Набор инструментов для учебных работ, собранный в один сайт: отчёты по DOCX-шаблонам,
блок-схемы и UML-диаграммы из исходного кода, решения задач по условию, всё с материалами
студента, пространствами для совместной работы и очередью заданий. Модель подключается любая
(своим ключом или общим ключом службы), а расход считается за инструменты, а не за токены
поставщика.

Версия 2.0 переписана с нуля относительно 1.0: вместо монолита — набор независимых пакетов
и одна HTTP-служба поверх них.

## Что умеет

| Модуль | Что делает |
|---|---|
| **Отчёты** | Берёт DOCX-шаблон с тегами `{{ключ:описание}}`, заполняет их значениями (текст, markdown, код, таблицы, картинки, схемы) — руками, моделью по тегу или моделью по всему отчёту, — хранит версии значений и собирает DOCX и PDF с превью первой страницы. У одной работы отчётов может быть несколько, каждый со своим бланком |
| **Блок-схемы** | Схема по ГОСТ из кода на Python, C++ и C# в формате draw.io: ветвления, циклы, ввод-вывод, по странице на функцию |
| **UML** | Диаграммы классов и объектов из кода тех же языков; объекты — статической трассировкой `main()`, код не выполняется; раскладка без наложений |
| **Решения** | Условие задачи файлом или текстом плюс пожелания → строение работы, блоки по стадиям, готовый архив с кодом и отчётом. У одной работы решений может быть несколько, у каждого своя папка контекста |
| **Агент** | Окно, в котором модель с инструментами работает над отчётом целиком: читает материалы, заполняет теги, строит схемы, показывает ход |
| **Материалы** | Хранилище файлов работы: PDF, DOCX, таблицы, картинки, исходники; разбор в отдельном процессе с лимитами, OCR сканов, сборка контекста для модели под бюджет токенов |
| **Пространства** | Личное и командные, роли owner / editor / viewer, приглашения, поиск по текущему пространству |
| **Аккаунт и админка** | Регистрация с ником, сессии по cookie, ключи API для `/api/v1`, аватар, планы с месячным расходом и квотой на диск, админка на отдельном домене под белым списком адресов |

## Быстрый старт

Нужны Docker и Docker Compose. Состояние службы живёт в томе `/data`, секреты — в `.env`
рядом с `docker-compose.yml`, вне репозитория.

    git clone https://github.com/MekoNix/Koritsu.git && cd Koritsu
    cp .env.example .env && $EDITOR .env     # KORITSU_SECRET и KORITSU_DOMAIN
    docker compose up -d --build

`KORITSU_DOMAIN=http://<адрес сервера>` (или `http://localhost`) поднимает сайт на порту 80
без TLS; с настоящим доменом Caddy выпустит сертификат сам. Сайт собирается внутри образа,
Node на хосте не нужен. Первая сборка тянет LibreOffice, tesseract и draw.io — образ службы
получается тяжёлым, это плата за PDF, OCR и PNG схем без внешних сервисов.

После подъёма:

1. Зарегистрируйтесь на сайте. Первому аккаунту право администратора ставится в базе,
   отдельного маршрута для этого нет:

       docker compose exec api python -c "import sqlite3; c=sqlite3.connect('/data/koritsu.db'); c.execute(\"UPDATE users SET is_admin=1 WHERE email=?\", ('you@example.com',)); c.commit()"

2. Ключ модели — в настройках аккаунта или общим ключом службы в `.env`
   (`KORITSU_PROVIDER_KEY_*`). Без ключа работают схемы, шаблоны, материалы и проверки, а
   прогоны модели отказывают понятной ошибкой.
3. Админка живёт на имени из `KORITSU_ADMIN_DOMAIN` и открыта только адресам из
   `KORITSU_ADMIN_ALLOW`; на основном имени `/admin` отвечает 404. Подробности — в
   `.env.example`, там описана каждая настройка.

## Устройство репозитория

    packages/
      api/            HTTP-служба: FastAPI, SQLite + Alembic, очередь заданий, SSE, модули
      orchestrator/   единственный, кто знает про все пакеты сразу: проект на томе, документы,
                      решения, промпты и инструменты модели
      hokoku/         отчёты из DOCX-шаблонов: теги, значения, подстановка, PDF
      fragmos/        блок-схемы из кода (tree-sitter → draw.io XML)
      uml_generator/  диаграммы классов и объектов
      kadai/          сценарий «условие → готовая работа» по стадиям
      materials/      хранилище материалов и сборка контекста для модели
      llm/            слой модели, не привязанный к поставщику: схемы JSON, инструменты, токены
      kyotsu/         общее для нескольких пакетов
    web/              сайт: React + Vite + TypeScript, клиент из OpenAPI, Playwright
    tests/            тесты службы и пакетов (pytest)
    Dockerfile        один образ на службу и воркер
    web/Dockerfile    сборка сайта внутри образа Caddy
    docker-compose.yml, docker-compose.dev.yml, Caddyfile, .env.example

Пакеты `hokoku`, `llm`, `materials`, `fragmos` и `uml_generator` друг о друге не знают —
их связывает только `orchestrator`, а с HTTP разговаривает только `api`. Из одного образа
поднимаются два контейнера: `api` отвечает на запросы, `worker` крутит очередь (прогоны
модели, LibreOffice, разбор файлов) с потолками памяти и времени на задание.

## Разработка

Python 3.12, Node 22, pnpm 9.

    python -m venv .venv && .venv/bin/pip install -r requirements.txt
    export PYTHONPATH=packages KORITSU_DATA_DIR=/tmp/koritsu KORITSU_SECRET=<строка от 32 байт>
    .venv/bin/python -m api migrate
    .venv/bin/python -m api serve --host 127.0.0.1 --port 8000
    .venv/bin/python -m api worker           # отдельным процессом

    cd web && pnpm install
    API_PORT=8000 pnpm dev                    # http://127.0.0.1:5173, /api проксируется на службу

Dev-состав compose (`docker-compose.dev.yml` поверх основного) открывает порт службы наружу
и отдаёт `web/dist` с диска после `pnpm build`.

Проверки:

    PYTHONPATH=packages .venv/bin/python -m pytest tests -q     # служба и пакеты
    cd web && pnpm lint && pnpm typecheck && pnpm test          # сайт
    cd web && pnpm e2e                                          # сквозные, стенд поднимает сам
    cd web && pnpm build && pnpm e2e:dist                       # боевая сборка

После правок маршрутов службы — `pnpm gen:api` в `web/`: клиент сайта генерируется из
`openapi.json`, и расхождение поймает `typecheck`.

## API

Служба документирована сама: `/openapi.json` и `/docs`. Сайт ходит в `/api/*` по cookie
сессии; для скриптов есть `/api/v1/*` с ключами API из настроек аккаунта. Долгие операции —
задания в очереди: `POST` возвращает `202` с идентификатором, ход приходит по SSE или
опросом.

## Выкат

Боевой состав — `docker-compose.yml`: миграции отдельным контейнером до всего остального,
`api`, `worker`, `caddy` (TLS и статика сайта, единственный, кто смотрит наружу) и `anubis`
(проверка работой перед сайтом). Наружу торчат только 80 и 443. Всё живое — в томе
`koritsu-data`, резервная копия — копия тома. Префикс пути `KORITSU_BASE_PATH` прячет сайт
от перебора, задаётся на сборке и в Caddy одинаково.

История версий — `CHANGELOG.md`, открытые и действующие решения — `status.md`.
