# Koritsu 2.0 (beta)

Набор инструментов для учебных работ, собранный в один сайт: отчёты по DOCX-шаблонам,
блок-схемы и UML-диаграммы из исходного кода, решения задач по условию, всё с материалами
студента, пространствами для совместной работы и очередью заданий. Модель подключается любая
(своим ключом или общим ключом службы), а расход считается за инструменты, а не за токены
поставщика.

Версия 2.0 переписана с нуля относительно 1.0: вместо монолита — набор независимых пакетов
и одна HTTP-служба поверх них.

## Что умеет

| Модуль | Что делает |
|---|---|
| **Отчёты** | Берёт DOCX-шаблон с тегами `{{ключ:описание}}`, заполняет их значениями (текст, markdown, код, таблицы, картинки, схемы) — руками, моделью по тегу или моделью по всему отчёту, — хранит версии значений и собирает DOCX и PDF с превью первой страницы. У одной работы отчётов может быть несколько, каждый со своим бланком. Отчёт можно собрать и без бланка — из задания: агент строит его блоками, а из готового отчёта делается бланк с тегами на полку шаблонов |
| **Блок-схемы** | Схема по ГОСТ из кода на Python, C++ и C# в формате draw.io: ветвления, циклы, ввод-вывод, по странице на функцию |
| **UML** | Диаграммы классов и объектов из кода тех же языков; объекты — статической трассировкой `main()`, код не выполняется; раскладка без наложений |
| **Решения** | Условие задачи файлом или текстом плюс пожелания → строение работы, блоки по стадиям, готовый архив с кодом и отчётом. У одной работы решений может быть несколько, у каждого своя папка контекста |
| **Доска** | Рукописное решение на доске Excalidraw (перо, мышь, палец), живое распознавание формул через MyScript, репетитор на модели: проверка по шагам, подсказка следующего шага, задача на тренировку. Ключи MyScript вводятся в настройках профиля |
| **Ассемблер** | Программа на TASM собирается настоящими TASM и TLINK в DOSBox-X и выполняется под отладчиком DebugX; вся трасса снимается за один прогон, и по ней ходят вперёд и назад в окне в духе Turbo Debugger: исходник, листинг, регистры, дамп, стек, вывод, справка по командам и агент, который объясняет программу по цифрам трассы. TASM и TLINK приезжают каталогом с машины выката |
| **Тренажёр** | Карточки «вопрос — ответ» из файла JSON с Markdown и формулами внутри (формат — [`docs/cards-format.md`](docs/cards-format.md)) или CSV, либо набор, написанный агентом по теме, списку вопросов к экзамену и файлам, с правкой черновика перед сохранением. Список вопросов в этот формат переводит и любая модель в любом чате — по готовому запросу с экрана загрузки ([`docs/cards-agent-template.md`](docs/cards-agent-template.md)). Заходы по своим настройкам: сколько вопросов, порядок, темы, только «Нет»; прогресс «знаю» виден только самому человеку и сохраняется при замене файла новой версией. Компьютер с клавиатурой и телефон со свайпами |
| **Агент** | Окно, в котором модель с инструментами работает над отчётом целиком: читает материалы, заполняет теги, строит схемы, показывает ход |
| **Материалы** | Хранилище файлов работы: PDF, DOCX, таблицы, картинки, исходники; разбор в отдельном процессе с лимитами, OCR сканов, сборка контекста для модели под бюджет токенов |
| **Пространства** | Личное и командные, роли owner / editor / viewer, приглашения, поиск по текущему пространству |
| **Аккаунт и админка** | Регистрация с ником, сессии по cookie, ключи API для `/api/v1`, аватар, планы с месячным расходом и квотой на диск, админка на отдельном домене под белым списком адресов |

## Быстрый старт

Нужны Docker и Docker Compose. Состояние службы живёт в томе `/data`, секреты — в `.env`
рядом с `docker-compose.yml`, вне репозитория.

    git clone https://github.com/MekoNix/Koritsu.git && cd Koritsu
    cp .env.example .env && $EDITOR .env     # KORITSU_SECRET и KORITSU_DOMAIN
    docker compose up -d --build

`KORITSU_DOMAIN=http://<адрес сервера>` (или `http://localhost`) поднимает сайт на порту 80
без TLS; с настоящим доменом Caddy выпустит сертификат сам. Сайт собирается внутри образа,
Node на хосте не нужен. Первая сборка тянет LibreOffice, tesseract и draw.io — образ службы
получается тяжёлым, это плата за PDF, OCR и PNG схем без внешних сервисов.

После подъёма:

1. Зарегистрируйтесь на сайте. Первому аккаунту право администратора ставится в базе,
   отдельного маршрута для этого нет:

       docker compose exec api python -c "import sqlite3; c=sqlite3.connect('/data/koritsu.db'); c.execute(\"UPDATE users SET is_admin=1 WHERE email=?\", ('you@example.com',)); c.commit()"

2. Ключ модели — в настройках аккаунта, раздел «Агент и модели»: свой ключ поставщика и,
   рядом с ним, модель, которой этот ключ работает. Общего ключа у службы нет — прогон идёт
   на ключе того, кто его завёл. Без ключа работают схемы, шаблоны, материалы и проверки, а
   прогоны модели отказывают понятной ошибкой.
3. Админка живёт на имени из `KORITSU_ADMIN_DOMAIN` и открыта только адресам из
   `KORITSU_ADMIN_ALLOW`; на основном имени `/admin` отвечает 404. Подробности — в
   `.env.example`, там описана каждая настройка.

## Устройство репозитория

    packages/
      api/            HTTP-служба: FastAPI, SQLite + Alembic, очередь заданий, SSE, модули
      orchestrator/   единственный, кто знает про все пакеты сразу: проект на томе, документы,
                      решения, промпты и инструменты модели
      hokoku/         отчёты из DOCX-шаблонов: теги, значения, подстановка, PDF
      fragmos/        блок-схемы из кода (tree-sitter → draw.io XML)
      uml_generator/  диаграммы классов и объектов
      zuhyo/          графики по данным (matplotlib): картинка для отчёта без исполнения кода
      kadai/          сценарий «условие → готовая работа» по стадиям
      kokuban/        доска: сцена → шаги решения → выжимка для репетитора → сверка ответа
      asm/            ассемблер: TASM и TLINK в DOSBox-X, трасса DebugX, память на шаге
      cards/          тренажёр: JSON и CSV → набор карточек, канонический JSON, план захода
      materials/      хранилище материалов и сборка контекста для модели
      llm/            слой модели, не привязанный к поставщику: схемы JSON, инструменты, токены
      kyotsu/         общее для нескольких пакетов
    web/              сайт: React + Vite + TypeScript, клиент из OpenAPI, Playwright
    tests/            тесты службы и пакетов (pytest)
    Dockerfile        один образ на службу и воркер
    web/Dockerfile    сборка сайта внутри образа Caddy
    docker-compose.yml, docker-compose.dev.yml, Caddyfile, .env.example

Пакеты `hokoku`, `llm`, `materials`, `fragmos`, `uml_generator`, `zuhyo`, `kokuban`, `asm` и `cards` друг о друге не знают —
их связывает только `orchestrator`, а с HTTP разговаривает только `api`. Из одного образа
поднимаются два контейнера: `api` отвечает на запросы, `worker` крутит очередь (прогоны
модели, LibreOffice, разбор файлов) с потолками памяти и времени на задание.

## Разработка

Python 3.12, Node 22, pnpm 9.

    python -m venv .venv && .venv/bin/pip install -r requirements.txt
    export PYTHONPATH=packages KORITSU_DATA_DIR=/tmp/koritsu KORITSU_SECRET=<строка от 32 байт>
    .venv/bin/python -m api migrate
    .venv/bin/python -m api serve --host 127.0.0.1 --port 8000
    .venv/bin/python -m api worker           # отдельным процессом

    cd web && pnpm install
    API_PORT=8000 pnpm dev                    # http://127.0.0.1:5173, /api проксируется на службу

Dev-состав compose (`docker-compose.dev.yml` поверх основного) открывает порт службы наружу
и отдаёт `web/dist` с диска после `pnpm build`.

Проверки:

    PYTHONPATH=packages .venv/bin/python -m pytest tests -q     # служба и пакеты
    cd web && pnpm lint && pnpm typecheck && pnpm test          # сайт
    cd web && pnpm e2e                                          # сквозные, стенд поднимает сам
    cd web && pnpm build && pnpm e2e:dist                       # боевая сборка

После правок маршрутов службы — `pnpm gen:api` в `web/`: клиент сайта генерируется из
`openapi.json`, и расхождение поймает `typecheck`.

## API

Служба документирована сама: `/openapi.json` и `/docs`. Сайт ходит в `/api/*` по cookie
сессии; для скриптов есть `/api/v1/*` с ключами API из настроек аккаунта. Долгие операции —
задания в очереди: `POST` возвращает `202` с идентификатором, ход приходит по SSE или
опросом.

## Выкат

Боевой состав — `docker-compose.yml`: миграции отдельным контейнером до всего остального,
`api`, `worker`, `caddy` (TLS и статика сайта, единственный, кто смотрит наружу) и `anubis`
(проверка работой перед сайтом). Наружу торчат только 80 и 443. Всё живое — в томе
`koritsu-data`, резервная копия — копия тома. Префикс пути `KORITSU_BASE_PATH` прячет сайт
от перебора, задаётся на сборке и в Caddy одинаково.

### Ассемблер: TASM и TLINK

DOSBox-X и DebugX стоят в образе, а Borland TASM и TLINK проприетарные и в репозиторий и
образ не входят. Их кладут каталогом на машину выката:

    mkdir -p asm-tools && cp /путь/к/TASM/{TASM.EXE,TLINK.EXE} asm-tools/
    # плюс всё, что им нужно рядом, если версия того требует (например RTM.EXE, DPMI16BI.OVL)

Каталог `asm-tools/` рядом с `docker-compose.yml` монтируется в `api` и `worker` только для
чтения в `/opt/asm-tools` и в `.gitignore` уже есть. Регистр имён файлов не важен. Без каталога
модуль в сайдбаре не показывается.

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `KORITSU_ASM_TOOLS_HOST` | `./asm-tools` | каталог TASM/TLINK на хосте (читает `docker-compose.yml`) |
| `KORITSU_ASM_TOOLS` | пусто (`/opt/asm-tools` в `.env.example`) | тот же каталог внутри контейнера; пусто — модуля нет |
| `KORITSU_ASM_TASM_VERSION` | `4.1` | версия TASM в корне каталога; версии в подкаталогах `<версия>/` находятся сами |
| `KORITSU_ASM_DOSBOX` | `dosbox-x` из `PATH` | исполняемый DOSBox-X |
| `KORITSU_ASM_DEBUGX` | `/opt/asm/debugx/DEBUGX.COM` | отладчик DebugX |
| `KORITSU_ASM_TIMEOUT_S` | `90` | секунд на весь прогон: сборку, трассу и перезапуски ради ввода; около 6 с на 100 000 шагов |
| `KORITSU_ASM_STEP_LIMIT_MAX` | `500000` | потолок лимита шагов, который можно выставить у программы |
| `KORITSU_ASM_SHOW` | нет | показывать модуль и без инструментов (для разработки сайта; прогоны отвечают 503) |

Готовность видна в `GET /api/asm/status`: по флагу на DOSBox-X, TASM, TLINK и DebugX.

### Ассемблер: MinGW x64 и исполнитель трасс

Режим «MinGW x64» собирает программу GNU `as` и `ld` для Windows x64 (пакет Debian, в основном
образе вместе с `libkernel32.a`), а трассу снимает под настоящим Wine x64 своим трассировщиком на
ptrace. Сборка идёт в воркере, исполнение — в **отдельном контейнере `asm-runner`**, и это не
перестраховка. Трассируемая программа — настоящий `prog.exe` на процессоре машины: Wine не мешает
ей звать системные вызовы Linux в обход Windows API и открывать файлы машины по пути `\\?\unix\`.
Воркер держит том данных и секреты `.env`, поэтому исполнять чужой код в нём нельзя. У
`asm-runner` нет ни сети, ни тома данных, ни `.env`, ни одной capability; корень только для
чтения, пишет он лишь во временный tmpfs, работает под своим UID, с потолками памяти, процессора
и числа процессов. С воркером его связывает только том очереди `asm-queue`: воркер кладёт туда
`prog.exe`, ввод и разобранный образ, исполнитель пишет шаги трассы, сырой вывод и итог. Протокол
описан в `packages/asm/mingw64/runner_service.py`.

Хосту нужен `kernel.yama.ptrace_scope` не выше 1 (так по умолчанию в Debian и Ubuntu): трассировщик
трассирует собственного потомка и прав `CAP_SYS_PTRACE` не просит, но при 2 и 3 ядро запрещает и это.

    cat /proc/sys/kernel/yama/ptrace_scope    # 0 или 1

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `KORITSU_ASM_MINGW_QUEUE` | пусто (`/queue` в `.env.example`) | том очереди исполнителя в воркере и службе; пусто — трассы MinGW x64 нет, сборка работает |
| `KORITSU_ASM_MINGW_PREFIX` | `x86_64-w64-mingw32-` | префикс имён `as`, `ld` и `objdump` |
| `KORITSU_ASM_MINGW_BIN` | поиск в `PATH` | каталог с `as` и `ld` |
| `KORITSU_ASM_MINGW_LIB` | `/usr/x86_64-w64-mingw32/lib` | каталог с `libkernel32.a` |
| `KORITSU_ASM_MINGW_STEP_LIMIT_MAX` | `20000` | потолок лимита шагов программы MinGW x64 (не больше 200 000) |
| `KORITSU_ASM_RUNNER_SLOTS` | `2` | прогонов одновременно в `asm-runner` (читает `docker-compose.yml`) |
| `KORITSU_ASM_RUNNER_TIMEOUT_MAX_S` | `300` | потолок времени одного прогона в исполнителе, что бы ни попросил воркер |
| `KORITSU_ASM_RUNNER_JOB_TTL_S` | `900` | задание старше этого удаляется из очереди исполнителем, даже если его никто не забрал |

Скорость — около 8 000 шагов в секунду от воркера до воркера, плюс 0,6 с на запуск Wine; вызов
функции kernel32 — один шаг. Готовность видна в `GET /api/asm/status`: трассировщик считается
установленным, пока исполнитель пишет в очередь свежее сердцебиение.

### Место на диске и журналы

Образы тяжёлые, и на машине выката это надо держать в голове:

| Образ | Размер | Из чего |
|---|---|---|
| `koritsu:local` | 2,44 ГБ | LibreOffice, tesseract, draw.io, DOSBox-X; binutils MinGW и `libkernel32.a` — около 30 МБ из них |
| `koritsu-asm-runner:local` | 1,44 ГБ | Wine x64 10.0 с библиотеками (1,3 ГБ), Python, префикс Wine 12 МБ |
| `koritsu-web:local`, `caddy`, `anubis` | десятки МБ | статика сайта и прокси |

Префикс Wine в образе исполнителя — 12 МБ вместо 770: файлы `system32`, совпадающие с DLL
пакета, заменены ссылками на них. Прогону заводится свой префикс поверх общего — около 2 МБ на
tmpfs — и удаляется после прогона при любом исходе.

Что растёт и чем ограничено:

- **журналы контейнеров** — `json-file` с ротацией у всех сервисов: 3 файла по 10 МБ;
- **очередь `asm-queue`** — задание удаляет воркер, забрав результат; брошенное — исполнитель по
  сроку `KORITSU_ASM_RUNNER_JOB_TTL_S`; шаги одного прогона — не больше 256 МБ, сырой вывод — не
  больше 64 МБ, вывод программы — не больше 1 МБ;
- **кэш сборки Docker** — после `docker compose build` в нём остаются гигабайты промежуточных
  слоёв (LibreOffice, Wine), и сам он не чистится.

После каждого выката со сборкой:

    docker builder prune -f          # кэш сборки: промежуточные слои
    docker image prune -f            # образы без тега, оставшиеся от прошлых сборок
    df -h /                          # под следующую сборку нужно 6 ГБ свободных

История версий — `CHANGELOG.md`, открытые и действующие решения — `status.md`.
